Safety design

Built to never lose money

Never pay twice

Preparations are idempotent per invoice — repeating a request returns the same payment, never a new one.

No silent retries

Expired prep, failed tx, missing events → record kept, human decides. Errors never trigger re-payment.

Tamper-evident signing

Server compares the hash of what Freighter signed against the prepared envelope. Changed body or fee-bump wrapper = rejected.

Secrets stay put

API token lives server-side only; signing keys stay in the wallet. Nothing sensitive in the browser.

EXAMPLE · DOUBLE-CLICK ATTACK

The client clicks “Approve & prepare payment” twice in a panic. The server looks up invoice #1, finds the payment it already prepared, and returns that same one. Result: one transaction, signed once, for 101 XLM — not 202.

Recovery

When things go wrong: “Check payment”

Observed on-chainApp behaviour
SUCCESS + matching payoutsMarks paid — never re-sends
PENDING / UNKNOWN / errorsKeeps the original record; re-check the same hash
Confirmed FAILEDKeeps the receipt; fix cause before a deliberate retry
Expired preparation / NOT_FOUNDRetains record; asks for support — no silent replacement
EXAMPLE · WI-FI DROPS MID-PAYMENT

Invoice #1 shows “paying”. The client clicks Check payment — the server finds the transaction hash, reads the ledger: SUCCESS, 90.9 and 10.1 both paid out. Invoice flips to paid. No new payment is created — the old one is simply confirmed.

EXAMPLE · WHY STROOPS + BIGINT

1 XLM = 10,000,000 stroops (integers). So 101 XLM = 1,010,000,000 stroops, split into 909,000,000 + 101,000,000.
If we used decimals, 0.1 + 0.2 ≠ 0.3 on a computer — with stroops, it's always exact.

Honest limits

What a production version still needs

  • A real database instead of orders.json
  • Authentication & ownership checks on checkout routes
  • Rate limiting and stricter request validation
  • A receipt verifier tuned to the exact production event schema
  • Mainnet only with a proper audit — this walkthrough is testnet-only
EXAMPLE · WHAT WOULD BREAK AT SCALE

Two freelancers share one deployed demo on free hosting. Freelancer A pays an invoice; the platform redeploys and orders.json resets. B's “check payment” can't find A's record — that's why recovery re-verifies by transaction hash instead.
